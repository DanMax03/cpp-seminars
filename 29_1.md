## C++ сложнее, чем кажется

**Пример 1:**
```cpp
long long foo(long long* a, int* b) {
    if (*a != 11) {
        *b = 11;
    }

    return *a;
}

int main() {
    long long a = 22;

    a = foo(&a, reinterpret_cast<int*>(&a));

    std::cout << a;  // ?
}
```

**Пример 2:**
```cpp
#include <iostream>

struct Base {
   virtual int f();
};

struct Derived : Base {
   int f() override {
      new(this) Base;
      return 1;
   }
};

int Base::f() {
   new(this) Derived;
   return 2;
}

int h() {
   Base b;
   int n = b.f();
   int m = b.f();
   return n + m;
}

int main() {
   std::cout << h() << std::endl;
}
```

## Почему так?

C++ компилируется в [LLVM](https://llvm.org/) - промежуточный язык. В этот язык так же компилируются Rust, Julia, Swift и даже Haskell.

Из LLVM уже получаются бинарные файлы. Идея в том, что на этом промежуточном языке можно делать большие тяжелые оптимизации, которые нет смысла переписывать на разных языках.

LLVM похож на ассемблер, только в его абстракции имеется бесконечное число регистров и типы. Отсюда же важный факт: LLVM ничего не знает об объектной модели C++, каких-то там переменных, ссылках на них. Он
оперирует значениями и указателями.

**Пример:**
```llvm
define dso_local void @test()
{
    %1 = tail call %struct.A* @get_object()
    %2 = bitcast %struct.A* %1 to void (%struct.A*)***
    %3 = load void (%struct.A*)**, void (%struct.A*)*** %2, !invariant.group !{}
    %4 = load void (%struct.A*)*, void (%struct.A*)** %3, !invariant.load !{}
    tail call void %4(%struct.A* %1)
}
```

## Strict aliasing

LLVM имеет отдельный модуль, посвящённый анализу зависимостей указателей: [Alias Analysis](https://llvm.org/docs/AliasAnalysis.html). В рамках этого анализа, например, LLVM устанавливает возможность пересечения
в памяти объектов, на которые указывают указатели.

**Объяснение примера 1:** `long long` и `int` - полностью разные типы. Их объекты не могут лежать в одном и том же месте, а значит `*b = 11` не может поменять объект под указателем `a`. Стало быть, второе чтение
в `return` можно соптимизировать, воспользовавшись тем значением, которое мы прочитали из `a` для сравнения в `if`.

## Время жизни объекта & переиспользование памяти

Второй пример очевидно поднимает вопрос: "А на сколько корректно писать `new(this)`?" Если подумать чуть шире, то можно прийти к вопросу о том, когда и как можно переиспользовать память под разные объекты.

Если почитать [стандарт](https://eel.is/c++draft/basic.life#def:initialization), то можно увидеть как выглядит время жизни объекта:
 1. Выделение памяти
 2. Вызов конструктора
 3. Деконструирование
    - Для типов-не-классов, это происходит в момент некоторого _уничтожения объекта_ (читай вызов пустого деструктора)
    - Для типов-классов, это соответствует вызову деструктора
    - Особенная ситуация: память по неизвестной причине просто начинает занимать новый объект! Тогда время жизни старого будет сразу завершено, начнётся время жизни нового объекта

Что можно делать с указателем на объект, когда он либо ещё не создан, либо уже уничтожен? (т.е. с его памятью за рамками времени жизни). [Стандарт](https://eel.is/c++draft/basic.life#7) говорит, что следующие ситуации - UB:
 - Вызов `delete`
 - Попытка обратиться к нестатическим членам класса
 - Почти любые конверсии указателя

Исключением из последнего пункта являются конверсии в `void*`, `char*`, `unsigned char*` или `std::byte*`. Указатели с подобным типом гарантированно имеют возможность читать любую память.

Ну и самое сочное: когда же можно создавать один объект на памяти другого? Стандарт определяет понятие [transparently replaceable](https://eel.is/c++draft/basic.life#9) объектов. Если объекты transparently replacable, то
создание одного на месте другого легально.

**Объяснение примера 2:** создаваемый объект на месте `Base` имеет тип `Derived != Base`. Следовательно, эти объекты не transparently replacable и их нельзя подменять.

**Пример:** из определения transparently replaceable следует, что наличие константного поля делает класс сразу не transparently replaceable
```cpp
struct X {
    const int n;
};

int main() {
    X* p = new X{42};
    new (p) X{7};
    std::cout << p->n;  // UB
}
```

## Анекдот, почему оно так всё работает и как с этим быть

**Пример:**
```cpp
struct X {
    const int n;
};

int main() {
    std::vector<X> v = {{42}};
    v.pop_back();
    v.push_back({1580});
    std::cout << v[0] << std::endl;  // UB???
}
```

И пример выше действительно был UB до C++17, пока не появилась мистическая функция `std::launder`. Чтобы понять её природу, нужно снова заглянуть в LLVM.

**Пример:**
```cpp
struct Base {
    virtual void f() {
        std::cout << 42 << std::endl;
    }
};

struct Derived : Base {
    void f() override {
        std::cout << 77 << std::endl;
    }
};

int main() {
    Base* b = new Derived;
    b->f();
    b->f();
    b->f();
}
```

Если бы мы в тупую компилировали этот код, то каждый вызов `f` является виртуальным и требует каждый раз сделать 3 вещи: загрузить виртуальный указатель, загрузить адрес функции из виртуальной таблицы и только потом
начать исполнение функции. Должно быть очевидно, что это можно было соптимизировать: 1 раз сходить в виртуальную таблицу, а затем просто сделать 3 вызова функции.

В LLVM конечно же подумали о том чтобы делать подобную оптимизацию. Для этого с каждым указателем ассоциируется _метаинформация_ - некоторые дополнительные знания об объекте, к которому ведёт указатель. В частности,
если мы знаем, что от вызова `b->f()` не меняется виртуальный указатель в `b`, а также никогда не меняется виртуальная таблица `Derived`, то LLVM способен провести оптимизацию загрузки значений (оно же _store to load optimization_).

Это, внезапно, согласуется со стандартом С++: определение transparently replaceable устроено так, что для виртуальных классов не может поменяться виртуальный указатель от вызова каких-либо виртуальных методов.

Аналогичная проблема возникает при использовании `const` полей: при их загрузке в метаинформации указателя сохраняется тот факт, что объект не меняется (а оптимизатор смотрит именно на информацию указателя, а не на реально происходящие
изменения в памяти, куда он указывает). 

На уровне LLVM конечно же придумали способ, как грамотно отключать свои оптимизации. Для этого они используют функцию `launder`, которая из переданного указателя создаёт новый, но стирает прежнюю метаинформацию (идея так же известна как
_equal-but-not-equivalent_).

И только начиная с C++17 в языке появилась функция-обёртка `std::launder`, которая выполняет те же функции, что и в LLVM.

**Замечание:** с точки зрения компиляции C++ в LLVM, `reinterpret_cast` - это использование того же указателя, просто на другой тип! Это в том числе касается метаинформации. Поэтому, если нужно получить новый указатель на объект
и приходится иметь дело с `reinterpret_cast`, то там же нужен и `std::launder`
